1. СИСТЕМА ДИСКАВЕРИ (ОБНАРУЖЕНИЕ НОД В СЕТИ)
--------------------------------------------------------------------------------
Как устроен вход в сеть:
• TON: Глобальный файл ton-global.config.json содержит стартовые DHT-ноды
  (IP, UDP-порт, публичный ADNL-ключ). Нода подключается к ним и через Kademlia DHT
  находит пиров. Сиды не требуют стейка.
• Stellereum (текущая реализация):
  - Публичные DNS TXT-записи (seeds.stellereum.org) в формате:
    stellereum/v1 node_id=inf1:<20B> ed=<32B> host=<IP/domain> port=<UDP> x=<32B>
  - Любой новый узел читает TXT-записи через UDP-резолвер (src/dns_seeds.rs)
    и связывается с пирами без ручной правки конфигов.
  - Сид-ноды — это публичные точки входа и архивы блоков, стейк им НЕ нужен.

2. СИСТЕМА ВЫБОРОВ ВАЛИДАТОРОВ ПО МОДЕЛИ TON ELECTOR
--------------------------------------------------------------------------------
Принцип работы в TON:
• Валидаторы НЕ прописаны в конфиге и НЕ статичны.
• Каждые 18–36 часов происходит эпоха выборов (Elections).
• Системный смарт-контракт Elector принимает заявки кандидатов со стейками.
• Elector сортирует кандидатов по величине эффективного стейка, формирует
  ValidatorSet на следующую эпоху (обычно 300–400 нод) и коммитит их ключи
  в блок мастерчейна.
• Сеть автоматически переключается на новый набор валидаторов на границе эпохи.
• По завершении раунда честные валидаторы получают награды + возврат стейка,
  а нарушители (downtime / equivocation) штрафуются слэшингом через Elector.

3. ПЛАН ПРИМЕНЕНИЯ В STELLEREUM (ПЕРЕХОД К MAINNET)
--------------------------------------------------------------------------------
Этап А (Текущий — Testnet Genesis v5):
• Consortium Allowlist в node.yaml + STELL_PEER_PQ_KEYS.
• Фиксированный набор валидаторов для стабильной отладки PQ-BFT v5 и Falcon-512
  без риска враждебного захвата кворума.

Этап Б (Mainnet):
• Системный SVM-контракт StakingElector (на базе SysCallStake / SysCallRotateValidatorKey):
  1. Эпохи консенсуса (например, 24 часа = ~120 000 блоков).
  2. Заявка на валидацию подаётся ончейн-транзакцией:
     - Блокировка бонда (минимум MIN_VALIDATOR_BOND = 1000 STELL).
     - Регистрация публичного Falcon-512 ключа и Ed25519 node ID.
  3. На границе эпохи состояние мастерчейна вычисляет новый активный ValidatorSet
     по формуле кворума ((total_power * 2) / 3 + 1).
  4. Формирование µQC-комитетов (16 нод на блок через BLAKE3-сортицию)
     производится автоматически из победившего набора эпохи.
  5. Слэшинг за даунтайм и эквивокацию списывается ончейн контрактом.

4. ТРЕБОВАНИЯ К ЖЕЛЕЗУ ВАЛИДАТОРОВ И ИХ РОСТ (HARDWARE SCALING)
--------------------------------------------------------------------------------
• Минимальные требования к оборудованию валидатора учитываются архитектурно:
  - Старт Testnet: 1–2 vCPU, 4–8 GB RAM, NVMe SSD, белый IP с открытым UDP.
  - По мере роста сети, роста TPS (>2 000 e2e) и включения параллельного исполнения
    (Sealevel-lite) минимальные требования повышаются:
    * Процессор: минимум 8–12 потоков (уровня AMD Ryzen 5 / EPYC / Intel Xeon)
      для параллельной валидации батчей Falcon-512 и верификации R1CS-контуров.
    * Память: 16–32 GB ECC RAM для быстрых in-memory шардов и буфера мемпула.
    * Диск: Высокоскоростной NVMe (IOPS > 50 000) для хранения Sled-стейта и истории.
    * Сеть: Выделенный симметричный канал 1 Gbps без NAT/шейпинга пакетов.
• Нода, отстающая по железу и задерживающая раунды, автоматически штрафуется
  за downtime и исключается из активного сета выборов.
