# Как работает почта InfMail — простыми словами

## Главная аналогия
Обычная почта: письмо лежит **в одном** почтовом ящике на **одном** сервере.
InfMail: письмо нарезано на куски, куски разложены по **разным компьютерам**
(нодам), а список «что где лежит» — в общей таблице (DHT), которую хранят все.

## Что происходит, когда ты жмёшь «Отправить»
1. Письмо режется на куски по 1 МБ.
2. Каждый кусок копируется на **3 ноды** (почему 3 и какие — ниже).
3. Получателю в его список «Входящие» дописывается номер письма.
   Тебе тот же номер дописывается в «Отправленные».
4. Всё. Тело письма хранится **один раз**, ссылаются двое.

## Что происходит, когда открываешь Входящие
1. Сервер берёт твой список номеров.
2. По каждому номеру находит куски на нодах, склеивает, проверяет целостность.
3. Показывает ленту. Полный текст тянет только для открытого письма.

## Папки, вложения, файлы, удаление
- **Папки** (Inbox/Sent/Spam/Trash…) — это просто разные списки номеров.
  Переложить письмо = переписать номер из списка в список.
- **Вложения** — отдельные куски рядом с письмом.
- **Файлы** — отдельное хранилище с папками, работает так же (куски + список).
- **Удалить** = вычеркнуть номер из своих списков. Куски с текстом остаются
  у собеседника и на чужих нодах. Стереть «везде и у всех» технически невозможно —
  так устроена любая распределёнка.

## Внешняя почта (gmail и т.п.)
Внутри сети свой протокол, наружу — обычный почтовый сервер-переводчик
(Stalwart): туда уходит через SMTP, оттуда забирается по IMAP раз в минуту.
Поэтому адрес существует в двух мирах сразу.

## Подписка
Платишь 0.5/5 TON кошельком → сервер видит платёж в блокчейне (проверяет
раз в 45 секунд) → включает тариф: почта 1→3 ГБ, файлы 0→6 ГБ.

## Шардинг: будут ли «3–4 шарда» при 100 нодах?

Короткий ответ: **шардов нет и не нужно**. Вот как распределяется нагрузка
на самом деле.

Каждая нода при создании получает **случайный номер** (id). Каждый кусок письма
тоже получает **случайный номер** (хэш). Кусок кладётся на **3 ноды с ближайшими
номерами** — это обычный Kademlia-DHT, как в торрентах.

Почему распределение равномерное, а не «трём конкретным»:
- номера кусков случайны → каждый кусок «падает» в случайную точку круга номеров;
- номера нод случайны → точки-ноды покрывают круг равномерно;
- итог: при 100 нодах каждая хранит примерно **3% всех кусков** (100 писем →
  ~300 кусков-копий → ~3 куска на ноду, плюс-минус).

Что меняется с ростом сети:
- **3 ноды** (сейчас): «3 ближайшие» = все подряд, репликация формальная.
- **10 нод**: куски начинают реально разъезжаться по разным машинам.
- **100 нод**: каждая держит ~3% данных; падение любой ноды незаметно —
  у каждого куска есть ещё 2 копии; чтение идёт с ближайшей живой.

Где настоящий предел — не место, а **популярность**: если одно письмо откроют
тысяча человек, все трое хранителей получат нагрузку. Лечится кэшем превью
(уже есть) и кэшем тел (пока нет — кандидат в следующие задачи).

Если когда-нибудь понадобятся именно шарды (например, разные юрисдикции данных
или платные/бесплатные зоны) — это будет деление круга номеров на диапазоны
со своими правилами. Сейчас для этого нет причин: RF=3 на плоском DHT даёт
и равномерность, и отказоустойчивость.

## Для программиста (компактно)

```
send:   POST /mail/send -> чанки×RF=3 (k-ближайшие по blake3) + манифест в DHT
                         + id в mail:{получатель}:index и mail:{отправитель}:sent-index
read:   GET /mail/inbox -> index_list -> fetch чанков -> blake3-сверка -> склейка
action: POST /mail/action -> перекладка id между mail:{email}:*-index
files:  POST/GET/DELETE /files, индекс files:{email}
plan:   nonce -> TON на Storage -> индексер 45с -> paid_until_ms
auth:   JWT typ=session + sid; удаление: POST /settings/account/delete
```

Константы: чанк 1 МБ, RF = min(кандидатов, 3), connect-таймаут 8с, кэш NFT 90с.
Проверено живым E2E: inbox 200/0.1–0.3с, send ~0.13с, подписка 0.6 TON → paid.
