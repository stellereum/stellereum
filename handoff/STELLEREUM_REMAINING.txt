--- A0. ПРОИЗВОДСТВЕННЫЕ БЛОКЕРЫ ВОЛНЫ W8.3 (закрыты 2026-10-21) ---

Три пункта из внешнего аудита были помечены как OPEN production blockers.
Все три закрыты; что осталось — это не дефекты, а честно записанные остатки.

[ЗАКРЫТО] A10. Лайт-клиент не был подключён к sync-пути.
  «Узел сам выдаёт корень, в который верит» — не доказательство для внешнего
  верификатора. Теперь: узел держит собственный LightClient на своём
  финализированном голове (заголовок с precommit-кворумом), каждый блок от
  пира при sync проверяется против этого якоря ДО применения
  (sync::verify_synced_blocks_against_anchor), узел отдаёт якорь и
  финализированные заголовки по RPC (stell_getFinalizedCheckpoint,
  stell_getFinalizedHeader), и есть внешний верификатор:
    stellereum light-client --from <rpc> --verify <адрес> --validators <файл>
  ОСТАЁТСЯ: валидаторский набор — это весь trust anchor (набор берётся
  ТОЛЬКО извне, никогда у проверяемого сервера); ротации набора нет.

[ЗАКРЫТО] A5. zk-SNARK-опкод — не настоящий ZK (повторный forward-pass).
  Что делает на самом деле — задокументировано честно (src/zkml_attestation.rs,
  module header): это SOUND re-execution-аттестация с BLAKE3-Merkle-трейсом и
  Fiat-Shamir, а НЕ SNARK/STARK: ни R1CS/AIR, ни polynomial commitment, ни
  pairings, ни trusted setup. Опкоды переименованы (SysCallVerifyZkMlIn ->
  SysCallVerifyZkMlReexec, SysCallVerifyZkMlSnark -> SysCallVerifyZkMlAttestation),
  а наружу отдаётся machine-readable capability statement:
  stell_zkmlCapabilities -> zero_knowledge:false, succinct:false, hiding:false,
  sound:true, trusted_setup:false.
  ОСТАЁТСЯ: реальный ZK-протокол (контур + commitment + транскрипт) — см. §2
  ниже и D-06 в docs/audits/KNOWN_ISSUES.md.

[ЗАКРЫТО] A8. STELL_AUTO_UPGRADE по умолчанию был 1.
  Теперь по умолчанию ВЫКЛ: живая миграция (execve нового бинаря) вооружается
  только явным STELL_AUTO_UPGRADE=1/true на конкретной ноде; опечатка падает
  безопасно; невооружённая нода на высоте апгрейда встаёт с кодом выхода 42
  (совместимо с Cosmovisor). Вооружённая нода печатает громкий баннер на
  старте. Путь апгрейда переаудирован: traversal имени, symlink кандидата,
  symlink родительского каталога и TOCTOU закрыты в коде
  (governance::stage_verified_upgrade_binary) и закреплены тестами.
  ОСТАЁТСЯ: решение о вооружении — операторское, поузловое (все ноды или
  ни одна); стейджинг кандидата — тоже операторская обязанность.

Подробно: docs/audits/KNOWN_ISSUES.md (KI-18, KI-24, KI-31, KI-33, раздел L),
docs/OPERATIONS.md §12, §12.1, §12.2, docs/RPC.md.

[ЗАКРЫТО] P2-15. Стандарт подписи кошелька (аудит P2 п.15).
  Был проприетарный SHA-256 seed («несовместим с чем-либо кроме своего CLI»)
  и не было задокументированного стандарта подписи сообщения/вызова.
  Теперь: docs/WALLET_SIGNING.md — преамбула байт-в-байт
  («Stellereum Signed Message:\n» + доменный тэг + chain_id + длина + тело,

  Формат транзакций и формат адресов НЕ менялись — только message-signing слой.

[ЗАКРЫТО] 15. Explorer с декодированными событиями + верификацией исходников.
  Декодированные события уже были (индексер: ABI-манифесты с ноды через
  stell_getContractAbi, эндпоинты /api/v2/contract/:address/events,
  /api/v2/tx/:hash/events, /api/v2/events). Не хватало второй половины:
  доказать, что задеплоенный WASM-блоб собран из заявленного исходника.
  Теперь (Sourcify-стиль, каноническая форма — текст .wat):
    нода: stell_verifyContractSource {contract, source|source_hex|source_hash,
      compiler, compiler_flags} -> {verified, onchain_code_hash,
      rebuilt_code_hash, source_hash} — перекомпилирует исходник тем же
      пайплайном, что деплой (wat-крейт), и сравнивает хэш пересборки с
      on-chain code_hash (принимаются оба исторических алгоритма: BLAKE3
      детерминированного деплоя и SHA-256 legacy-deploy; эталон — хранимый
      хэш, не пересчёт). Строго read-only; чужой compiler/флаги/подмена
      исходника — REFUSED (verified:false), не ошибка и не угадывание.
      stell_getContractSource — зарегистрированный source_hash + verified.
      ContractRegistry хранит опциональный source_hash (BLAKE3(source_text),
      коммитится в trie рядом с code_hash; absent = unverified и в дайджест
      ничего не вносит — корни legacy-цепей байт-в-байт те же).
      Единственная мутация — stell_registerContractSource, только явным
      подписанным действием создателя (ed25519 над
      b"STELL_REGISTER_SOURCE"||contract||source_hash).
    индексер: таблица verified_contract_sources {contract, source_text,
      compiler, flags, verified_at}; POST /api/v2/contract/:address/verify
      (шлёт исходник на ноду, пишет строку ТОЛЬКО при verified:true —
      локально не решает никогда) и GET /api/v2/contract/:address/source
      (verified-текст или честный 404).
  Модель доверия: verified:true доказывает лишь побайтовое равенство
  on-chain байтов пересборке из данного текста данным пайплайном — НЕ
  безопасность исходника. См. src/contract_source.rs (модуль-документация),
  docs/RPC.md (§8, trust model), тесты: cargo test --lib contract(_source),
  индексер-тесты.
  ОСТАЁТСЯ: полный reproducible-build для не-wat тулчейнов (Rust->wasm и
  т.п. — там канонической формы пока нет, только wat-путь); ротация
  скомпрометированного исходника — повторной регистрацией (истории версий
  нет, хранится одна метка).

--- A. БЕЗОПАСНОСТЬ (открыто из ручного аудита) ---

F-A. Range proofs + solvency для shielded-пула [HIGH, предусловие unshield].
  Сейчас: apply_transfer проверяет только уравнение (sum_in - sum_out == fee*G)
  + spent-set. Отрицательные балансы легальны, входы — произвольные точки,
  владения не доказывается. Прямого воровства нет (дебет всегда по tx.from),
  но ЛЮБОЙ будущий вход/выход (shield/unshield), читающий баланс как сумму, —
  бесконечный минт. Чинить ДО появления unshield: range proofs на выходы +
  доказательство остатка/владения.
F-G. Bridge refund [MEDIUM, нужен дизайн, не патч].
  Парковка в эскроу односторонняя; Release монет не двигает; таймлок нечем
  оспорить. При ошибке адреса/отказе релееров — вечный лок. Варианты:
  refund-after-expiry (риск двойной траты через цепи) vs challenge-механизм.
F-J. Snapshot-sync не тащит домены [MEDIUM, предсуществует].
  sync.rs восстанавливает только accounts; session/bridge/confidential/zkML/
  cross-shard наборы теряются. Нужны fetch+verify доменных блобов в sync-пути.
Worker-panic клин [LOW, защита есть]. В воркере ApplyLane нет catch_unwind:
  детерминированно-паникующий блок = вечный клин ноды. Сегодня защита — fuzz +
  1146 тестов без паник; unwrap'ы check-guarded. Кандидат: catch_unwind с
  громкой парковкой или доказательство panic-freedom.

--- D. ИННОВАЦИИ (отдельный трек, после базового) ---

[ ] 1. Communication Grants — реестр грантов (scope, срок, revoke) + доставка
[ ] 2. Нативный AA — аккаунт-контракт по умолчанию (WASM-движок есть)
[ ] 3. Опциональная приватность — режимы (прозрачный/скрытый получатель/сумма)

    РАЗБОР (аудит 2026-10-05, честно как есть):
    Сколько приватности реально дают режимы:
    - Прозрачный: обычная открытка (А→Б, сумма видна). Как сейчас везде.
    - Скрытая сумма: в цепи только математика-коммитменты, сумму не видит
      никто. НО отправитель ВСЕГДА виден (tx.from + nonce + публичная оплата
      газа), а получатель скрыт ТОЛЬКО при свежем одноразовом stealth-адресе.
      Анонимности как у Monero нет и не будет (RingCT запрещён паспортом).
      Оценка: конфиденциальность сумм — да; анонимность — нет. Уровень
      Zcash-shielded-lite, но БЕЗ range proofs (F-A открыт: отрицательные
      балансы легальны — перед unshield чинить обязательно).
    - Скрытый получатель: работает только с гигиеной (не переиспользовать
      адреса, иначе графы склеиваются по времени/повторам).
    Возмутятся ли биржи? Нашим дизайном — почти наверняка нет:
    биржи боятся (а) Travel Rule (нужны отправитель/получатель — отправитель
    у нас ВСЕГДА публичен); (б) санкций (скрининг идёт по АДРЕСАМ, а не
    суммам); (в) делистинга (снимают МОНЕТЫ С ОБЯЗАТЕЛЬНОЙ приватностью вроде
    Monero, а у нас приватность опциональна + дефолт прозрачный + viewing keys
    для аудита — выжившая модель Zcash/Litecoin-MWEB). Точечный риск: stealth-
    получатели усложняют beneficiary-инфу; биржевые депозиты почти наверняка
    потребуют ТОЛЬКО прозрачный режим (нормально, настраивается политикой).
    Ломает ли контракты/пулы? Нет — проверено по коду: shielded-пул изолирован
    (своё состояние, свой digest), ордербук/PMМ/стейкинг/мосты его не читают;
    тела акторов confidential вызывать НЕ могут (fail closed); газ ВСЕГДА
    публичный (каждый приватный перевод привязан к публичному аккаунту).
    Единственный будущий стык — unshield/shield entry-exit: ЗАБЛОКИРОВАН за F-A.
    Зачем вообще: коммерческая тайна сумм (зарплаты, платежи, HFT-стратегии не
    светятся конкурентам) + viewing keys для комплаенса. Приватность как РЕЖИМ,
    а не как личность монеты — ровно так инновация и записана.
[ ] 4. Безопасные мосты — optimistic verification, окно оспаривания, timelock, лимиты

    БОЛЬШАЯ ЗАМЕТКА: почти нативный защищённый мост (аудит 2026-10-05).
    Цель: мост, для взлома которого надо сломать СРАЗУ несколько независимых
    механизмов (а не один, как Ronin/Poly/Wormhole/Nomad/Harmony). "Почти
    нативный" = факт депозита доказывается математикой чужой цепи, а не
    словами релееров. "Невзламываемых" не бывает — бывает цена взлома выше добычи.

    СЛОЙ 0 — что уже живёт в коде (база, не трогать, только расширять):
    кворум 2/3 distinct-подписей + fail-closed на пустом множестве;
    replay-set (один кредит на source_tx_hash); таймлок 1ч для крупных (порог
    50k STELL, мелочь идёт мгновенно); rate limit 500k/час (глобальный);
    mint caps (500k/час + 100M суммарно, audit F-H); персист replay-набора
    (переживает рестарты); адаптеры TON/EVM/Solana с реальной проверкой
    evidence (BoC-хэши, MPT-пруфы чеков, бинарные SHA-256 Merkle-пруфы).

    СЛОЙ 1 — optimistic-ядро + окно оспаривания (сердце инновации):
    депозит принимается оптимистично, разблокировка — только через окно
    (30-60 мин). В окне ЛЮБОЙ вотчер может подать fraud-доказательство
    ("такого депозита в чужой цепи нет/сумма не та") и отменить + получить
    награду. Допущение меняется с "честны 2/3" на "достаточен ОДИН честный
    наблюдатель". Нужны: новые intent'ы (Challenge с доказательством, Resolve),
    правило разрешения споров (детерминированное, из данных цепей), бонды
    вотчеров (slash за ложный вызов, награда за поимку), очередь оспариваемых.
    Технологии: те же Merkle/Patricia-примитивы, что уже в репо; fraud-доказательства
    вида "header H не содержит tx T" = Merkle-proof отсутствия либо контр-заголовок
    с большим весом/seqno.

    СЛОЙ 2 — light-клиент (настоящая "нативность", по цепям):
    проверять консенсус чужой цепи прямо у нас, вместо доверия релеерам:
    - TON: masterchain seqno + множество валидаторов мастерчейна + Merkle-пруф
      транзакции в блоке (наш BoC-код переиспользуется один в один);
    - EVM/Ethereum/Arbitrum: beacon sync committee (512 валидаторов, BLS-агрегат —
      у нас уже есть BLS12-381 и batch-verify!) + receipt/transaction MPT-пруфы
      (наш PatriciaTrie — тот же крипто-примитив, cpat2);
    - Solana: слоты + vote-state якорей, SHA-256 Merkle-инклюжн (уже реализован
      в адаптере), confirmations по слотам вместо времени.
    Что нужно: подача настоящих заголовков (см. Вотчеры), хранение валидаторных
    множеств чужих цепей on-chain (компактно: толькоinstruments смены эпох),
    проверка их подписей в консенсусе (детерминирована, без сети).
    Честный предел: реорг глубже confirmations и 51%-атака самой чужой цепи
    не лечатся никаким мостом — только глубиной подтверждений.

    СЛОЙ 3 — вотчеры (off-chain демоны, без них слои 1-2 слепые):
    3 демона (TON/EVM/Solana): следят за финализацией, строят evidence
    (инклюжн-пруфы +depth), сабмиттят в нашу цепь; отдельно challenge-вотчеры
    для окна оспаривания. Им нужны: RPC-эндпоинты чужих цепей, ключи, бонды,
    экономика (награда за evidence/challenge-поимку из комиссий моста).
    Это инфра/ops, не консенсус. Консенсус только ПРОВЕРЯЕТ то, что вотчеры
    принесли (граница уже зафиксирована в коде адаптеров).

    СЛОЙ 4 — изоляция и стоп-краны (чтобы один провал не топил всё):
    per-chain изоляция эскроу и лимитов (взлом TON-леги не трогает ETH-легу);
    пауза моста через governance (аварийный стоп по аномалии объёма);
    refund-трек (аудит F-G открыт: нужен дизайн refund-after-expiry vs
    challenge — без знания оффчейн-состояния refund = двойная трата!).
    Скорость vs таймлок: мелочь — мгновенно (уже); крупняк — мгновенно через
    LP fast lane за fee (строить; Across-модель: LP фронталит из своего кармана
    под свой бонд, каноника дозревает в локе); расчёты — медленно и безопасно.

    СИБИЛ-ВОПРОС: "а если раскидает по 100 кошелькам?" (аудит 2026-10-05).
    Честный ответ по уровням:
    1. Глобальные крышки ДЕРЖАТ ВСЕГДА, независимо от числа кошельков: 500k/час
       на весь мост + 100M суммарно. Хоть тысяча адресов — больше не вытечет.
       Это задняя стена, она не обходится.
    2. Per-sender окно (предложено: сумма адреса за 24ч > порога → таймлок)
       сибил режет ЧАСТИЧНО: 100 чистых кошельков × под порогом = проходят.
       Поэтому per-sender — дополнение, а не основа.
    3. Кластеризация по графу финансирования: 100 кошельков почти всегда
       запитываются из ОДНОГО источника (кран/биржа/мастер). У нас вся native-
       история прозрачна → общий источник виден on-chain. Правило: общий бюджет
       на кластер с общим финансированием (детерминировано из данных цепи —
       годится в консенсус, в отличие от ML-эвристик).
    4. Привязка к НАЗНАЧЕНИЮ, а не только к отправителю: N кошельков, выводящих
       на ОДИН внешний адрес (или связанные), агрегируются в один лимит/лок.
       Деньги всегда куда-то идут — destination не размножишь бесплатно.
    5. Тиры по истории/стейку (как KYC-уровни у бирж, но без KYC): свежий адрес —
       низкий лимит; aged-аккаунт + стейк — высокий. Сибил-ферме из 1000 свежих
       кошельков достаются только детские лимиты; накрутить возраст/стейк тысяче
       адресов — дорого и медленно, и всё равно прозрачно.
    6. Честный предел: терпеливый, богатый атакующий с 1000 чистых выдержанных
       кошельков ВСЁ РАВНО будет капать по капле. Неостановимо без identity.
       Цель — не невозможность, а: медленно (глобальные крышки) + дорого
       (фандинг-следы, возраст, стейк) + видимо (вся подготовка прозрачна).
       Идеальная сибил-устойчивость = identity-слой, это уже инновация 5
       territory (имя→адрес + репутация), а не мостовая механика.

    ЧЕКЛИСТ ИНВАРИАНТОВ МОСТА (живой; любое изменение кода моста обязано пройти
    все пункты + тесты на каждый; обсуждено 2026-10-05, НЕ реализовано — стадия
    обсуждения):
    [ ] И1. Нет фиксированных ключей: кворум только от коммитнутого стейк-множества
        (ротируется); захват ключей сам по себе недостаточен для кражи.
    [ ] И2. Нет привилегий в коде: ни админ-ключей, ни доверенных флагов, ни
        ролей — только детерминированные правила, одинаковые для всех нод.
        (`trusted` игнорируется на apply — уже так.)
    [ ] И3. Непроверенное не принимается: каждое сообщение проверяется
        (inclusion/linkage), сомнения = отказ (fail closed), не пропуск.
    [ ] И4. Минт ограничен инвариантом: hourly + cumulative caps в committed-
        стейте (уже живёт: 500k/ч + 100M). Безлимитного минта нет ни при каком
        кворуме.
    [ ] И5. Кража не мгновенна: таймлок крупных (1ч, уже) + окно оспаривания с
        fraud-доказательствами (строить) + вотчеры с бондами (строить).
    [ ] И6. Изоляция: провал одной цепи не трогает эскроу/лимиты других;
        пауза моста через governance при аномалии объёма.
    [ ] И7. Рестартоустойчивость: replay-наборы, очереди, окна, счётчики mint —
        всё в персисте (уже: bridge/confidential/cross-shard деревья); рестарт
        не открывает ни одну закрытую защиту. Новое состояние — только
        с персистом сразу.
    [ ] И8. Доказательство вместо доверия (путь к нативности): факт депозита
        проверяется математикой чужой цепи (заголовки + подписи их валидаторов),
        не словами релееров. Этапы: вотчеры-демоны → header store on-chain →
        проверка подписей в консенсусе.
[ ] 5. Идентичность имя→адрес: `name.stl` как NFT-объект (типа user.ton/user.eth,
    НЕ web2-DNS/Workspace). Реестр имён, резолв в аккаунт, регистрация с защитой
    от сквоттинга, expiry/продление, передача имени как NFT.
